  0) Immediate “does it compile / run” checklist
  ========================================
  A. Alarm sound will not play (core functionality gap)

    - AlarmActivity only stops the service (Dismiss/Snooze), but never starts it.
  What to do
  1) Start AlarmForegroundService when an alarm fires (best place: AlarmReceiver).
     - In AlarmReceiver.onReceive():

       - also launch (or notify) AlarmActivity in a compliant way (see section 2).
  2) Ensure AlarmActivity is started from a user-visible path (full-screen notification) to avoid background-launch restrictions.

  B. Smart Window / Wake window extras are ignored
  - AlarmScheduler schedules different intents with extras:
    - FAILSAFE, WINDOW_START, HARD_STOP (AlarmScheduler.kt)

  C. Unit test contains a wrong expected value (will fail)

    - exactlyOneRemCycle_whenSleepIsNinetyMinutes expects 1410 (11:30 PM)

  What to do
  - Change expected list to [30] for that test, or clarify that the function should return “REM boundaries before bedtime” (unlikely).

  D. Repository / Flow scope usage could leak work
  - RemSettingsRepositoryImpl uses its own CoroutineScope(Dispatchers.IO) with SharingStarted.Eagerly.
  - If repeated construction happens, multiple eager collectors can exist.
  What to do
  - Prefer injecting a shared scope (viewModelScope) or use stateIn(viewModelScope, WhileSubscribed, initial).
  - Or make repositories singletons via DI.

  ========================================
  2) Alarm reliability and Android behavior (must-fix for real users)
  ========================================
  A. Background activity launch restrictions
  - Starting an Activity directly from a BroadcastReceiver can be blocked or unreliable on modern Android versions unless it is driven by a high-priority alarm/notification flow.
  What to do (recommended pattern)
  1) In AlarmReceiver:
     - Start AlarmForegroundService immediately (so audio can begin even if UI is delayed).
     - Post a high-importance notification with a FullScreenIntent pointing to AlarmActivity.
     - Mark category as ALARM and set priority high.
  2) In AlarmActivity:
     - Keep showWhenLocked/turnScreenOn (already set in manifest)
     - Provide Dismiss/Snooze actions that:
       - stop AlarmForegroundService
       - cancel the current alarm(s) and schedule snooze / next cycle
  3) If you want “Clock app” grade behavior:
     - Consider AlarmManager.setAlarmClock(AlarmClockInfo) for user-visible alarms.
     - This also helps with system treatment of alarms.

  B. Android 13+ notification permission
  - targetSdk is 36; for Android 13+ you need runtime POST_NOTIFICATIONS to show notifications (including foreground service notifications).
  What to do
  - Add <uses-permission android:name="android.permission.POST_NOTIFICATIONS" /> in manifest.
  - Request permission at runtime on first launch (or before enabling alarms).

  C. Exact alarm policy
  - You request SCHEDULE_EXACT_ALARM.
  - On Android 12+ this is “special app access”; Play policies expect a strong justification for exact alarms.
  What to do
  - Provide in-app explanation when enabling alarms.
  - Consider using setAlarmClock() to align with alarm clock use-case.
  - Ensure you handle the case where the user denies exact-alarm access:
    - degrade gracefully or guide to settings.

  D. Doze + failsafe strategy
  - You schedule a failsafe 10 minutes after the main alarm.
  - Current receiver ignores FAILSAFE extra; there is no difference in behavior.
  What to do
  - Use FAILSAFE to change behavior:
    - If main alarm didn’t ring or wasn’t dismissed, failsafe should re-trigger sound/UI aggressively.
    - Or re-start service and raise notification again.

  ========================================
  3) Smart Window (REM mode) correctness
  ========================================
  Right now, Smart Window is mostly UI + scheduling plumbing, but not decision logic.

  What’s missing
  A. Definition of “smart”
  - The UI suggests: “Waking during light sleep” via REM timing.
  - But the scheduler currently:
    - schedules a window start and a hard stop
    - then immediately rings on whichever alarm fires (because AlarmReceiver has no logic)
  So the alarm rings at windowStart (not “best REM time”) and also can ring at hardStop.

  What to implement (minimum viable Smart Window)
  1) Decide the actual trigger time once per night
     Option 1 (simple):
     - Compute candidate REM times from bedtime + cycle length (already in TimeModel.computeRemWakeTimes)
     - Choose the candidate time that is closest to the target alarm time, but not after hard stop.
     - Schedule exactly one alarm at that chosen time (plus a failsafe).
     - This avoids two alarms and avoids “ringing early always”.
  2) If you insist on “window start + hard stop”:
     - At WINDOW_START: begin checking for “awake signals” or run a lightweight strategy
     - When you decide it’s time to ring: ring once and cancel the hard stop.
     - At HARD_STOP: ring only if not already rung.

  B. Single source of truth for time math
  - You currently have:
    - AlarmTimeCalculator.computeTriggerTimeMillis(nowMillis, hour24, minute) for next day logic
    - Time12 extensions for minutes conversions
  Keep everything in one place and write tests for:
  - target time near midnight
  - bedtime before/after midnight
  - cycle lengths not 90
  - “closest REM time within window” selection

  C. UI semantics confusion
  - The “REM Smart Mode” switch toggles AlarmMode, not remEnabled.
  - remEnabled appears to be a separate feature flag stored in RemSettingsStorage, but there is no visible switch for it in MainActivity.
  What to do
  - Decide which toggle the user understands:
    - If Smart Mode is the feature: remove remEnabled entirely or expose it clearly.
    - If remEnabled is intended as a master flag: add a switch and gate Smart Mode behind it.

  4) Awareness feature (currently dead code)
  ========================================
  Current state
  - receiver/UserAwakeReceiver.kt cancels alarms when ACTION_USER_PRESENT fires.
  - It is not registered (no intent-filter in manifest; no dynamic registration), so it never triggers.

  What to do
  A. Decide what “awareness” means
  - If you only want “if user is already awake, don’t ring”:
    - Cancelling the alarm when the user unlocks might cancel the alarm for the next day too, which is probably wrong.
    - You likely want “mark as awakened today” and only suppress within the current alarm window.
  B. Implement properly
  Option 1: Dynamic registration (recommended)
  - Register a BroadcastReceiver in a foreground-visible component (MainActivity / a service) for:
    - ACTION_USER_PRESENT
    - ACTION_SCREEN_ON (optional)
  - Persist a “userAwakeToday” timestamp and check it in AlarmReceiver before ringing.
  Option 2: Use sensor/activity APIs (heavier)
  - Step count, motion, etc. Not needed for MVP.
